# Сетевые наказания, проверка при входе и чат (форк koiie111)

Документ описывает, как плагин применяет наказания на сети серверов с общей БД, и что именно он гарантирует.
Версии платформы: .NET 10, CounterStrikeSharp.API 1.0.369 (`MinimumApiVersion(369)`).

## 1. Область действия: наказания сетевые, права — нет

* **BAN, GAG, MUTE, SILENCE и WARN действуют на всех серверах с общей БД.** Ни один запрос наказаний не фильтрует по
  `server_id`: ни чтение, ни снятие (`css_unban/ungag/unmute/unsilence/unwarn`), ни истечение, ни кеш банов, ни подсчёт
  счётчиков/истории/предупреждений, ни онлайн-время (TimeMode 0).
* `server_id` по-прежнему **записывается** в строку — как сведение о том, где наказание выдано. Столбцы не удалены, схема и
  SQL-миграции не менялись. `NULL`, `0` и «устаревший» id другого сервера не влияют на решение.
* **`MultiServerMode` больше не влияет на наказания.** Параметр оставлен, чтобы старые конфиги загружались; значение `false`
  ведёт себя как `true`. Права администраторов, группы и серверные настройки (`sa_admins.server_id`,
  `sa_groups_servers`) остаются серверными — это другая область действия.
* Источник выдачи не важен: другой сервер, сайт, онлайн/офлайн-команда, API.
* Истёкшие и снятые наказания не действуют. Постоянное наказание (`duration = 0`) не истекает из-за `ends`
  (в БД `ends` у него фиктивный = время выдачи): в SQL и в памяти длительность 0 проверяется раньше `ends`.
* TimeMode: `1` — до `ends` по реальному времени; `0` — по минутам онлайна (`passed`, `NULL` = 0). Начисление минут идёт
  идемпотентно (compare-and-set), одна запись начисляется один раз. Исчерпание минут **не отмечается в памяти по `id`**
  из чтения пакета: оно запускает свежее чтение игрока в его упорядоченной очереди (см. §3).
* **IP-адреса никогда не банят.** `BanType`, `IgnoredIps`, общий IP, история IP, `CheckMultiAccountsByIp` не участвуют ни в
  решении при входе, ни в проверке онлайн-игроков: игрок отклоняется только за бан своего SteamID64. Параметры оставлены,
  чтобы старые конфиги загружались (`BanType 1` по-прежнему пишет IP в новые строки банов для сайта, `CheckMultiAccountsByIp`
  — только админское уведомление о связанных аккаунтах). `css_banip` банит онлайн-игроков с этим IP по их SteamID; для адреса
  без игрока строка не создаётся (её ничто бы не применило).

## 2. Вход игрока: решение принимает общая БД

1. `OnClientAuthorized` (void в CounterStrikeSharp 1.0.369) и `player_connect_full` создают **одну сессию подключения**
   (slot + userid + SteamID64) и ставят загрузку в очередь БД. SteamID = 0 (авторизация не закончена) проверкой не считается:
   загрузка не стартует, пока SteamID не подтверждён.
2. Бан по подтверждённому SteamID64 читается **из БД параметризованным запросом по SteamID** на каждое подключение
   (`status = 'ACTIVE'` и `duration <= 0 OR ends IS NULL OR ends > now`; граница `ends == now` — бан закончился, как в SQL-джобе
   истечения). Результат не зависит от `BanType`, IP, `IgnoredIps`, `CheckMultiAccountsByIp`, `server_id` и от свежести
   локального кеша. Бан, выданный на другом сервере за секунду до входа, находится; бан, снятый секунду назад, не блокирует.
3. Кандидатов из кеша нет: локальный кеш банов в решении не участвует (ни положительно, ни отрицательно). Дозаполнение
   пустых `player_ip`/`player_name` в строке бана идёт только по SteamID игрока.
4. Активные GAG/MUTE/SILENCE читаются из БД в той же загрузке и применяются до любых второстепенных операций.
5. **Что гарантируется по времени.** `OnClientAuthorized` не умеет отклонять рукопожатие, поэтому это **не синхронный
   pre-auth reject**: игрок отключается (`Disconnect`) сразу, как приходит ответ БД, то есть через время одного запроса
   после авторизации (обычно миллисекунды, при медленной БД — до её таймаута). Отключение не зависит от `KickTime`,
   пешки, оружия, эффектов и от вспомогательного `banid`/`UnlockConCommands`.
6. Запись IP (`sa_players_ips`, нужна сайту) выполняется отдельным заданием: её задержка или ошибка не откладывают
   решение и отключение. Статистика (счётчики, уведомление админам) загружается после применения ограничений; её ошибка
   оставляет счётчики нулевыми и никак не влияет на наказания (контракт b43a6b7/fbabb7a пересмотрен именно так).

### Сбой проверки

Ошибка БД, таймаут, переполнение очереди, плагин не в состоянии `Ready`, неготовый кеш — **не** «наказаний нет». Такое
подключение остаётся непроверенным, загрузка повторяется с задержкой (2, 5, 15, 30, затем 60 с).
`OtherSettings.UnverifiedConnectionTimeoutSeconds` (по умолчанию **45**, допустимо 10–600) ограничивает ожидание: по
истечении срока сессия, не дошедшая до состояния *Loaded*, отключается (`NETWORK_DISCONNECT_REJECT_INVALIDCONNECTION`),
в лог пишется диагноз (состояние загрузки, число попыток, состояние плагина, последняя ошибка). Игроку при этом **не
записывается** ни бан, ни другое наказание. Уже проверенные игроки при падении БД не отключаются; последний известный набор
ограничений сохраняется.

## 3. Онлайн-игроки: синхронизация

Раз в проход обслуживания (61 с) для каждого загруженного онлайн-игрока ставится задание чтения его активных записей
**в его персональную упорядоченную очередь** (`Runtime.TryQueueDbOrdered`, ключ — SteamID64), то есть после всех ранее
принятых mute/unmute/connect-load этого игрока и до всех последующих. Ответ применяется на игровом потоке, только если
сессия всё ещё текущая (slot + userid + SteamID).

* Новая запись добавляется; изменённая (продление, замена на более долгую/постоянную) заменяет прежнюю; запись, которой нет
  в ответе (снята/истекла на другом сервере), удаляется; несколько перекрывающихся записей и типов поддерживаются
  (в памяти запись несёт `sa_mutes.id`).
* Записи, принятые **после** чтения (команда на этом сервере), устаревшим ответом не удаляются; снятый мут устаревшим ответом
  не воскрешается (порядок очереди гарантирует, что чтение раньше unmute применилось раньше него).
* Успешный пустой ответ снимает записи; ошибка чтения не меняет ничего (исключение, а не «пусто»).
* `VoiceFlags.Muted` ставится/снимается только этим битом; голос освобождается лишь когда не осталось ни MUTE, ни SILENCE.
* Hot reload плагина: нативный бит `Muted` живёт в `CPlayer` и не сбрасывается выгрузкой managed-плагина (только `CPlayer::Disconnect`).
  Поэтому первая успешная загрузка после reload выравнивает бит по итоговому состоянию слота (БД-строки, записи, принятые
  за время чтения, API-записи) в обе стороны: мут, снятый на сайте до синхронизации, больше не оставляет игрока без голоса;
  активный MUTE/SILENCE бит сохраняет. Остальные voice-биты не трогаются; ошибка чтения/timeout/полная очередь бит не меняют.
  Проверено только managed-тестами (`VoiceBitTests`), не на реальном CS2 (там не проверялось).
* Предел задержки: новое/изменённое/снятое наказание достигает онлайн-игрока этого сервера **не позже следующего прохода
  (≈ 61 с) плюс время очереди БД**. Бан онлайн-игрока: в каждом проходе БД читается пакетами по 64 SteamID
  (`player_steamid IN @ids`, активный и не истёкший), `Disconnect` получают ровно те подключения, что были проверены (slot +
  userid + SteamID + текущая сессия) (≤ ≈ 61 с). Ошибка чтения никого не отключает, следующий проход проверяет снова. Redis для этого не используется и не нужен; `RedisInform` остаётся
  только уведомлением.
* **TimeMode 0, порядок синхронизации и онлайн-кредита.** Чтение пакета «использованные минуты» выполняется общим
  неупорядоченным заданием и поэтому **не применяется к памяти само**: оно лишь определяет игроков, у которых мут исчерпан,
  и для каждого ставит ещё одно упорядоченное чтение (то же `QueueMuteSync`, тот же `Reconcile`). Чтение берёт место в очереди
  игрока на игровом потоке, выполняется после всех ранее принятых чтений (их применение — часть их задания) и видит строку
  такой, какая она сейчас. Поэтому (A) устаревшая синхронизация не воскрешает истёкший мут — следующее чтение в очереди идёт
  после неё и убирает запись; (B) продление той же строки сайтом/другим сервером не снимается результатом чтения старой
  версии — решает свежее чтение. Голос согласуется сразу при применении этого чтения (только бит `Muted`, перекрывающийся
  MUTE/SILENCE сохраняется), без ожидания следующего таймера. Если очередь переполнена, снятие откладывается до следующего
  прохода (небезопасного направления нет). TimeMode 1 не затронут.
* Один запрос на игрока (в своей очереди) вместо общего пакета — осознанная цена порядка операций; пакетное чтение
  (`GetActiveMutesBatchAsync`) используется там, где порядок не нужен.

## 4. Отключение (`Helper.KickPlayer`)

Обе перегрузки идут через `KickFlow`: **обязателен только `Disconnect`**. Заморозка/окраска/блокировка оружия — украшение;
отсутствие пешки, мёртвый или наблюдающий игрок, `WeaponServices == null`, исключение в эффекте или в `banid` его не
отменяют. Немедленный кик не подавляется ранее выставленным `WaitingForKick`. Отложенный кик не держит контроллер: таймер
заново находит слот и отключает только то же подключение (slot + userid + SteamID64), поэтому переиспользованный слот
не затрагивается.

## 5. Чат для GAG/SILENCE

Глобальный слушатель команд (`AddCommandListener(null, …)`) выполняется до обработчика чата движка. В CounterStrikeSharp 1.0.369
строка `!cmd` печатается движком в `Host_Say` (если не «тихий» `/`), а затем отдельно диспетчеризуется как `css_cmd`;
`HookResult.Stop` из слушателя на `say` отменяет **и то, и другое**. Поэтому для игрока с GAG/SILENCE:

* `say`/`say_team` с обычным текстом, `@…`, с пробелами/кавычками перед триггером — блокируются (с уведомлением).
* Строка с триггером (`!текст`, `!hello`, `!hello world`, `/текст`, `!!x`, `! x`, неизвестная команда, цепочки через `;`,
  кавычки, управляющие символы, длинная строка) — блокируется без каких-либо действий.
* **Собственные команды плагина классифицируются по исходному ключу, а не по имени алиаса** (`CommandCatalog` /
  `OwnCommands`). Таблица алиасов строится при регистрации команд (`Commands.json`), на сообщении выполняется один поиск в
  неизменяемой таблице. Переименованный `css_psay → css_tell` остаётся «доставляет текст» и блокируется в консоли и через
  триггер. Классы: *Safe* — позитивный список проверенных ключей, отвечающих только вызвавшему (`css_penalties`, `css_admin`,
  `css_adminhelp`, `css_who`, `css_disconnected`, `css_warns`, `css_history`, `css_players`, `css_hide`, `css_hidecomms`);
  *PublishesText* — `css_say`, `css_psay`, `css_csay`, `css_hsay`, `css_cssay`, `css_asay`, `css_vote`; *Other* — остальные
  (администрирование с аргументами, причинами, именами…). Через триггер игрока с GAG/SILENCE выполняются только *Safe*
  (под любым алиасом) и команды **других плагинов** из `GagAllowedChatCommands`; имя собственной команды в этом списке
  игнорируется. Команды других плагинов с `say` в имени и неизвестные блокируются по подстроке, как раньше.
* **Общий guard в самих callback'ах** (`ChatGuard.MayPublish`) стоит первой строкой во всех callback'ах, доставляющих текст
  вызвавшего другим игрокам (`basechat.cs`: 6 команд, `css_vote`), поэтому защита не зависит от пути `say` и от имени
  алиаса. Серверная консоль (`caller == null`) не ограничивается. Тест проверяет наличие вызова guard в IL каждого
  callback'а из `PublishingKeys`. Причины банов/киков/варнов, имена `css_rename` и подобные — часть сообщений об
  административных действиях (`ShowActivityType`), а не рассылка текста игрока, и этим guard'ом не закрываются.
* **Подключение, чьи наказания ещё не прочитаны, тоже не публикует текст** (`ChatRestriction.Unverified`: сессия слота не
  относится к этому подключению или не в состоянии *Loaded*): обычный вход до ответа БД, SteamID = 0, горячая
  перезагрузка, смена карты, повторный вход, переиспользованный слот. Строки отбрасываются с коротким сообщением.
  Начальная загрузка читает БД и *заменяет* всё прежнее состояние слота, записи прошлого владельца слота не наследуются.
* Игрок только с MUTE пишет как обычно (MUTE ограничивает голос, GAG — текст, SILENCE — оба канала).
* `UserMessageGagChatType = true` включает вторую линию: пользовательские сообщения SayText2 (118) автора с GAG/SILENCE
  отбрасываются независимо от локализатора и даты окончания.

**Границы совместимости.** Плагин не может отфильтровать любой `PrintToChat` стороннего плагина: перехватываются слушатель
команды `say*` и сообщение 118. Если сторонний chat processor зарегистрирован раньше этого плагина, его слушатель выполняется
раньше (слушатели вызываются в порядке регистрации) и уже мог разослать текст; если позже — видит остановленную команду.
Плагин, который сам формирует вывод без SayText2 с индексом автора (или с другим автором), для хука 118 невидим. Рекомендуется
загружать SimpleAdmin раньше chat processor'ов и проверять на стенде (см. §7).

## 5a. Горячая перезагрузка и подключения без проверки

CounterStrikeSharp загружает перезагруженный плагин в новый `AssemblyLoadContext`: статическое состояние прежнего экземпляра
перенести нельзя (и не переносится), а новый экземпляр сразу начинает с пустых наказаний. Раньше повторная загрузка игроков
стартовала только через 6 с и ждала БД, в этот промежуток текст был разрешён. Теперь `Load` сразу создаёт сессии для всех
подключённых людей (`AdoptConnectedPlayers`, также при `css_plugins load` посреди карты); пока БД не ответила, они —
*Unverified* (нет свободного текста, см. §5), затем применяются GAG/SILENCE из БД. Поведение при медленной/недоступной БД:
подключение остаётся *Unverified*, загрузка повторяется с задержкой, по `UnverifiedConnectionTimeoutSeconds` (от момента
перезагрузки) оно отключается — так же, как при обычном входе; ничего не записывается. Слушатель, увидевший человека без своей
сессии (пропущенное событие), сам запускает загрузку и до её конца считает его *Unverified*.

## 5b. Срок проверки и SteamID = 0

Срок общий для подключения (slot + userid) и считается от первого момента, когда плагин его увидел, в том числе пока
SteamID = 0. Таймер ставится один раз (`DeadlineArmed`); сессия с подтверждённым SteamID наследует начало отсчёта и признак, повторные
события авторизации, `player_connect_full` и повторы загрузки срок не продлевают. По истечении отключается только
*текущая* непроверенная сессия именно этого подключения (SteamID = 0 никогда не считается «не забанен»), причина в логе —
техническая; наказание за недоступность БД не создаётся.

## 5c. Порядок эффектов при выдаче наказания

GAG/MUTE/SILENCE (`LocalPenalty.Issue`): сначала задание предлагается ограниченной очереди; только после принятия добавляются
локальное ограничение и бит `VoiceFlags.Muted`. При переполнении очереди или неготовом плагине нет ни записи в БД, ни
локального наказания, ни изменения голоса; админ получает прежнее сообщение об отказе. То же для эффекта заморозки у `css_warn`.

## 6. Настройки

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `OtherSettings.UnverifiedConnectionTimeoutSeconds` | 45 | Срок непроверенного подключения (10–600 с). |
| `OtherSettings.GagAllowedChatCommands` | `[]` | Команды **других плагинов**, доступные игроку с GAG/SILENCE через триггер (свои команды плагина решаются списком проверенных ключей). |
| `OtherSettings.BanType`, `IgnoredIps`, `CheckMultiAccountsByIp` | — | Не влияют на баны (IP не банит). |
| `MultiServerMode` | `true` | Устарел и игнорируется для наказаний. |

## 7. Нагрузка на игровой поток

Замер управляемого кода на этой машине (не нативный стенд): строка чата игрока с GAG (restriction + решение) ≈ 0,13 мкс и
0 B аллокаций; игровая часть постановки синхронизации 128 игроков (`QueueMuteSync`) ≈ 1,6 мс на проход раз в 61 с. На
сообщении нет SQL, обхода игроков, копирования реестра и перестройки множеств (таблица алиасов строится при регистрации).
Добавленная работа игрового потока в проходе: одна постановка до 128 упорядоченных заданий (после исчерпания минут) и один
пакетный элемент отключения. p95/p99 таймеров и глубина очереди на живом сервере с 64/128 игроками **не измерялись** (нет стенда).

## 8. Проверки

`dotnet test tests/CS2-SimpleAdmin.Tests` — поведенческие тесты на реальных БД (SQLite; MySQL 5.7/8.0, MariaDB 10.11 при
`SA_TEST_MYSQL`/доступных портах, `SA_REQUIRE_MYSQL=1` делает недоступный сервер ошибкой): сеть серверов при обоих
значениях `MultiServerMode` и любых `server_id`, SteamID-бан при любых `BanType`/IP/`IgnoredIps`, IP не банит (в том
числе строки с изменённым IP и устаревший кеш), пакетная проверка онлайн-игроков, границы `ends`, оба порядка TimeMode 0
(`ReviewFollowUpTests`: управляемые барьеры между чтением и применением), отказ очереди, срок проверки для SteamID = 0,
запрет текста до проверки, доставка голосования (N вызовов `PrintToCenter`), реальный реестр команд (все ключи,
алиасы по умолчанию, `css_psay → css_tell`, `!vote`),
вставка бана после последнего обновления кеша и обратный случай, отказ чтения ≠ «пусто», срок проверки, независимость
стратегии от IP/статистики, синхронизация (добавить/продлить/второй тип/снять/перекрытие/ошибка/чужой слот),
`KickFlow`, решения чата.

**Не проверялось без стенда CS2:** замеры p95/p99/max таймеров и очереди на 64/128 игроках, волна переподключений,
медленная БД под нагрузкой, реальные `Disconnect`/`VoiceFlags`/чат на двух серверах с общей БД, получение
сообщений вторым клиентом, совместимость с установленным chat processor. Эти проверки остаются за владельцем сервера.
